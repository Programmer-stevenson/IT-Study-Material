Designing for the cloud is a different skill

Cloud systems design uses managed services, elastic scaling, and pay-per-use economics to build things that would take a warehouse of hardware and a team of engineers to do the old way. It also has its own traps — cost sprawl, distributed system complexity, and the illusion that "the cloud will handle it" (it won't).

This guide takes you from what cloud design is, through the actual process, the Well-Architected pillars, the building blocks, patterns, and tradeoffs — using Azure as the primary reference (aligned with your AZ-900 → AZ-104 path) with AWS notes where useful.

// Azure-centric with AWS equivalents · Beginner to intermediate · Vendor-neutral principles, cloud-native application

01

What cloud systems design actually is

Not "put my server in the cloud" — designing systems that use cloud primitives natively.

Cloud systems design is the discipline of building applications and infrastructure using cloud-native services, elastic resources, and consumption-based economics. It's not just "hosting your app somewhere else" — that's called lift-and-shift, and while it's a valid migration step, it's not what makes cloud powerful.

Real cloud design leans into what only the cloud gives you:

  • Elasticity — resources appear when you need them, disappear when you don't
  • Managed services — the cloud runs the database, the queue, the load balancer — you build on top
  • Global reach — deploy in dozens of regions worldwide without owning a single data center
  • Pay-per-use — no upfront hardware costs; you pay for what you actually consume
  • Higher-level primitives — instead of "install a database on a Linux server," you request a managed database and Azure handles the rest
The mindset shift from on-prem to cloud
On-prem thinkingCloud-native thinking
Buy servers up frontProvision resources as needed
Design for the worst-case peak loadDesign to scale up/down with actual load
Install and maintain everythingUse managed services where possible
Single data centerMultiple regions and availability zones
Servers are pets — you know them by nameServers are cattle — interchangeable and replaceable
Uptime through avoiding failureUptime through embracing and recovering from failure
Fixed costs, predictableVariable costs, requires active management
◈ The most important mindset shift

In on-prem, failure is abnormal and something you try to prevent. In cloud, failure is normal — servers die, services blip, regions have bad days — and you design to recover from failure rather than prevent it. This flip is the single biggest thing that separates cloud-native design from lift-and-shift thinking.

02

Service models and deployment models

The vocabulary that every cloud design conversation starts with.

Service models — how much the cloud manages for you
IaaS · Infrastructure as a Service
You rent VMs, storage, and networking. You manage the OS and everything above. Most control, most responsibility.
Azure: Virtual Machines · AWS: EC2 · GCP: Compute Engine
PaaS · Platform as a Service
You deploy code; the cloud manages the OS, runtime, and infrastructure. Less control, less operational burden.
Azure: App Service · AWS: Elastic Beanstalk · GCP: App Engine
SaaS · Software as a Service
Finished software delivered as a service. You just use it. No infrastructure or code to manage.
Microsoft 365 · Salesforce · Google Workspace
FaaS / Serverless
You write functions; the cloud runs them per-event. Pay per execution, scale automatically to zero when idle.
Azure: Functions · AWS: Lambda · GCP: Cloud Functions
CaaS · Container as a Service
You package apps in containers; the cloud runs them with orchestration.
Azure: AKS, Container Instances · AWS: EKS, ECS, Fargate
DBaaS · Database as a Service
Managed databases — the cloud handles patching, backups, HA. You just use the database.
Azure SQL, Cosmos DB · AWS: RDS, DynamoDB
Deployment models — where the cloud lives
Public cloud
Provider owns and operates infrastructure; multi-tenant; accessed over the internet. Azure, AWS, GCP.
Private cloud
Dedicated to a single organization. On-premises or hosted by a provider. More control, higher cost, less elasticity.
Hybrid cloud
Combination of public + private (or on-prem). Sensitive workloads stay private; scalable workloads use public.
Multi-cloud
Using services from multiple public providers (Azure + AWS + GCP). Avoids vendor lock-in, adds complexity.
Edge computing
Compute close to where data is generated (retail stores, factories, IoT). Reduces latency, offloads central cloud.
◈ The right level of abstraction

Junior instinct: go all-IaaS because "I want control." Senior instinct: use the highest level of abstraction that fits the requirements. Managed services (PaaS, DBaaS) mean less code to write, less to maintain, and less to break. Every layer of the stack you don't have to run yourself is a layer that isn't on your pager. IaaS is for when you genuinely need the control — legacy apps, specific compliance needs, or when the managed option doesn't fit.

03

The cloud design process

How to actually go from "we want to build this" to a working cloud architecture.

1
Understand the business need
Same as any design — but for cloud you also ask: what growth is expected? Are we replacing on-prem, extending it, or building something new? What's the tolerance for downtime? Are we prioritizing cost, speed, or reliability?
2
Requirements — functional and cloud-specific
Functional (what the app does), non-functional (the "-ilities"), and cloud-specific: which regions, latency targets, compliance zones (data residency), integration with existing on-prem, disaster recovery expectations, and target cost.
3
Constraints — the invisible walls
Cloud budget, existing licenses (Azure Hybrid Benefit for Windows/SQL is real money), team skills (do you know Azure or AWS?), corporate cloud choice, compliance (HIPAA, PCI, GDPR — some govern which regions and which services you can use).
4
Capacity + cost estimate
This is where cloud design differs from on-prem. Use the Azure Pricing Calculator or AWS Calculator to estimate monthly cost before deploying. Cost is a first-class requirement in cloud, not an afterthought. Get it wrong by 5x and the project gets canceled.
5
Choose the service model
IaaS, PaaS, serverless, containers? Start with the highest abstraction that fits (PaaS or serverless) and drop lower only if requirements force it. "We need Kubernetes because it's cool" is a red flag; "we need Kubernetes because we have 50 microservices and complex orchestration" is a real reason.
6
Sketch the architecture using cloud primitives
Draw it with real Azure services labeled: Front Door → App Service → Azure SQL + Cache for Redis + Blob Storage, with Application Insights watching everything. Use the actual product names — it forces you to be concrete.
7
Design for the Well-Architected pillars
Walk through each pillar (next section) and check: is the design reliable? Secure? Performant? Cost-optimized? Operationally sound? This is the checklist that catches gaps before production.
8
Plan for failure — the "what if" pass
What if the primary region fails? What if the database gets corrupted? What if traffic spikes 10x? What if the app has a bug that crashes it? For each: is there a designed recovery path, or a "we'd panic and fix it live" gap?
9
Iterate, document, and get review
Show the design to a peer or architect. Document decisions ("we chose Azure SQL over Cosmos DB because...") — this is invaluable a year later when someone asks "why did we do it this way?"
◈ Cost is a design constraint, not a bill

In on-prem, cost is decided when hardware is bought; the design just uses what's there. In cloud, every design decision has a monthly recurring cost. Choosing a bigger VM tier, a premium storage account, or a global load balancer directly changes the bill. Cost has to sit in the design process — it's not something the finance team resolves later.

04

The Well-Architected Framework — cloud design's rubric

Microsoft and AWS each publish "well-architected" frameworks. They're the checklist every cloud designer should internalize.

The Azure Well-Architected Framework defines five pillars that every cloud workload should be evaluated against. If your design does well on all five, it's likely a good design. Weakness on any pillar is a real vulnerability.

1. Reliability
The workload's ability to recover from failures and continue functioning. Multi-region deployment, availability zones, health checks, retry logic, backup and disaster recovery. Design for failure as normal, not exceptional.
2. Security
Protecting data, systems, and assets. Identity as the perimeter (Zero Trust), encryption in transit and at rest, secrets in Key Vault, network segmentation, defense in depth, principle of least privilege. Security is a pillar, not a phase.
3. Cost Optimization
Getting the value you need at the lowest reasonable cost. Right-sizing resources, using reserved instances / savings plans for steady workloads, spot instances for interruptible workloads, auto-scaling to avoid over-provisioning, monitoring spend with budgets and alerts.
4. Operational Excellence
Running and monitoring systems to deliver value continuously. Infrastructure as code, automated deployments (CI/CD), monitoring and observability (Application Insights, Log Analytics), incident response processes, runbooks for common issues.
5. Performance Efficiency
Using resources efficiently to meet demand. Choosing the right service and tier, scaling appropriately, caching hot data, using CDN for static content, optimizing database queries, load testing before production.

(AWS's Well-Architected Framework has an additional sixth pillar for sustainability — environmental impact of cloud choices. Azure covers this within the other pillars.)

◈ How to actually use it

For every design you make, walk through the five pillars deliberately. Ask "is this reliable?" (would it survive a region outage?). "Is it secure?" (are secrets in Key Vault, is traffic encrypted, is identity right?). "Is it cost-optimized?" (are we over-provisioned, using the right tier?). "Operationally excellent?" (can we deploy and monitor it?). "Performant?" (does it scale, is it fast?). If any answer is weak, that's the next thing to fix in the design.

06

Cloud design patterns

Proven architectures that appear again and again because they solve real problems well.

Basic web application (three-tier)

The workhorse pattern. Front Door / CDN → App Service → Azure SQL + Cache for Redis + Blob Storage, with Application Insights and Log Analytics watching everything. Scale App Service and the database independently; add caching for hot data.

Microservices with Kubernetes

Multiple independent services in containers, orchestrated by AKS. Behind an API Management gateway. Each service owns its data (own database instance). Service Bus or Event Grid for async communication. Complex — use when the org and workload justify it.

Serverless event-driven

Event source (Storage upload, HTTP request, queue message) → Azure Function → outputs to another service. Pay only for executions. Great for spiky, event-driven work. Common example: image upload triggers Function that generates thumbnails and writes them back to storage.

Data pipeline / analytics

Data sources → Event Hubs (streaming ingestion) → Stream Analytics or Databricks (processing) → Data Lake Storage + Synapse Analytics (warehouse) → Power BI (visualization). Modern analytics stack.

Hybrid cloud

On-prem network connected to Azure via VPN Gateway or ExpressRoute. Common patterns: extending Active Directory to Entra ID for identity, using Azure for burst capacity or DR site, keeping sensitive workloads on-prem while running new services in cloud.

Multi-region for high availability

Deploy the workload in two or more Azure regions. Front Door routes users to the nearest healthy region. Data replicated across regions (SQL geo-replication, Cosmos DB multi-region writes). Survives entire region outages — for real HA at 99.99%+ SLA.

◈ Common pattern — modern SaaS web application

User request flow:

1. User hits app.example.com — DNS resolves to Azure Front Door.

2. Front Door serves static assets from its cache; dynamic requests go to the nearest App Service instance.

3. App Service authenticates via Entra ID, then queries Azure SQL Database. Hot reads are served from Cache for Redis.

4. User uploads a file → App Service writes to Blob Storage → publishes event to Event Grid → Azure Function processes the file async.

5. All of this is monitored by Application Insights and Log Analytics; secrets live in Key Vault; costs tracked via Cost Management.

That's a real, production-shaped design — this is what a lot of cloud jobs actually look like.

07

Scaling in the cloud

Cloud makes horizontal scaling trivial and auto-scaling routine — if you design for it.

Vertical vs horizontal — the cloud takes

Vertical (scale up): Move to a bigger tier — B2s → D4s → D8s. Fast and easy in cloud. But it's still one instance; if it dies, everything's down. Good for databases and stateful workloads.

Horizontal (scale out): Add more instances behind a load balancer. This is where cloud shines — auto-scale rules can add/remove instances automatically based on CPU, queue length, or custom metrics. Design apps to be stateless so any instance can handle any request.

Auto-scaling patterns
  • Metric-based: Scale out when CPU > 70% for 5 minutes; scale in when < 30% for 10 minutes
  • Schedule-based: Scale up before 9 AM business hours; scale down at night
  • Queue-based: Scale workers based on queue length (10 messages per worker)
  • Predictive: AI-powered scaling that anticipates load based on history
Caching — cloud-specific tools
  • Azure Cache for Redis: In-memory data store for session state, hot data, computed results
  • CDN / Front Door: Edge caching of static content globally
  • App-level caching: Output caching in App Service, query result caching
  • Database read replicas: Azure SQL geo-replicas for read scaling
Database scaling in cloud
  • Vertical: Move to a higher DTU or vCore tier. Easy first move.
  • Read scaling: Read replicas — reads go to replicas, writes to primary
  • Elastic pools: Multiple databases share a resource pool for cost efficiency at scale
  • Sharding: Split data across multiple database instances by key. Complex — last resort.
  • Cosmos DB / DynamoDB: NoSQL databases designed for horizontal scale from day one
◈ Statelessness is the enabler

Auto-scaling only works if your app instances are stateless — meaning any instance can handle any request without needing local state. Store session state in Redis, files in Blob Storage, data in the database. If you have local files or in-memory state on each instance, horizontal scaling breaks. Cloud-native design starts with stateless services.

Reliability in cloud

Cloud gives you the tools for high availability — but only if you design to use them.

The cloud availability hierarchy
Protection scopeAzure mechanismWhat it survives
Rack failureAvailability SetsHost / rack failure within a data center
Data center failureAvailability ZonesFull data center loss within a region
Region failureMulti-region deployment + paired regionsFull Azure region outage (rare but real)
Provider failureMulti-cloudAzure itself having a bad day (very rare, extreme complexity)
The 9s and what they cost you
  • 99% (2 nines): ~87 hours/year downtime. Any single service basically.
  • 99.9% (3 nines): ~8.76 hours/year. Single-instance PaaS services typically.
  • 99.95%: Zone-redundant deployment (VMs or PaaS in Availability Zones).
  • 99.99%: Multi-region active-passive with automated failover.
  • 99.999%: Active-active multi-region with real-time replication. Very expensive and complex.
Recovery objectives
RPO
Recovery Point Objective — how much data loss you can tolerate. Backup frequency drives this.
RTO
Recovery Time Objective — how fast you must be back after a disaster. Automation and pre-provisioned standby drive this.
Azure Site Recovery
Managed DR service — replicates workloads to a secondary region for failover.
Azure Backup
Managed backup service for VMs, databases, and file shares with retention policies.
Failure patterns to design against
  • Retry with exponential backoff: Transient failures should trigger retries; don't hammer a struggling service
  • Circuit breaker: Stop calling a failing dependency temporarily to give it time to recover
  • Bulkhead: Isolate failures so one failing component doesn't take down others
  • Health checks: Load balancers only send traffic to instances passing health checks
  • Graceful degradation: When a non-critical service is down, keep core functionality working
◈ The SLA math trap

Composite SLA is calculated by multiplying, not averaging. If your app depends on Service A (99.9%) and Service B (99.9%), your composite is 99.9% × 99.9% = 99.8%. Chain more dependencies and the SLA drops fast. Every service you add is a potential availability hit. This is the argument for redundancy at each layer and for embracing async / decoupled architectures where a dependency failure doesn't take down the whole system.

Cloud security

The shared responsibility model is the whole game — knowing what's yours vs. the cloud's.

The shared responsibility model
LayerIaaSPaaSSaaS
Physical securityCloudCloudCloud
Network infrastructureCloudCloudCloud
HypervisorCloudCloudCloud
Operating systemYouCloudCloud
Runtime / middlewareYouCloudCloud
Application codeYouYouCloud
DataYouYouYou
Identity and accessYouYouYou
ConfigurationYouYouYou

Data and identity are always yours. No matter the service model. The cloud provider can't protect you from a leaked credential or a misconfigured storage account.

Zero Trust — the current standard
  • Verify explicitly: Every request authenticated and authorized, not just perimeter-based
  • Least privilege access: Users and services get only the permissions they need
  • Assume breach: Design as if attackers are already inside; limit blast radius
Cloud security building blocks
Entra ID (identity)
Central identity provider. SSO, MFA, Conditional Access policies.
Managed identities
Cloud resources have their own identities — no stored credentials in code.
Key Vault
Secrets, keys, certificates. Access controlled via Entra ID.
Network Security Groups
Firewall rules at subnet or NIC level.
Azure Firewall
Managed cloud firewall with threat intelligence.
Web Application Firewall
Filters malicious HTTP requests (SQL injection, XSS, OWASP Top 10) — attached to Front Door / App Gateway.
Private Endpoints
Access PaaS services via private IP inside your VNet — no public internet exposure.
Defender for Cloud
Security posture management + threat detection across your Azure resources.
Encryption in transit
TLS on all endpoints. Non-negotiable.
Encryption at rest
Default on all Azure storage services. Customer-managed keys available for extra control.
◈ Most cloud breaches are misconfigurations

The most common cause of cloud data breaches isn't a novel attack — it's publicly-exposed storage accounts, over-permissioned service principals, or leaked API keys in code. Cloud security is 80% "did you configure it right?" and 20% "sophisticated attack." Use Azure Policy to prevent bad configurations. Use Defender for Cloud to catch drift. Rotate secrets. Never put keys in source code.

Cloud cost — the pillar juniors underestimate

Cloud gives you the ability to build anything. It also gives you the ability to bankrupt the business overnight.

In on-prem, cost is decided at purchase and forgotten. In cloud, every design decision has an ongoing bill, and bad decisions compound daily. Cost is a first-class design pillar.

Cost optimization techniques
  • Right-sizing: Match VM tier to actual usage. Most orgs over-provision; downsize what's underused.
  • Reserved instances: Commit to 1-3 years of usage for 30-70% discount on steady workloads.
  • Savings plans: Flexible commitment on compute spend — similar discount, more flexibility.
  • Spot / Low-priority VMs: Up to 90% discount for interruptible workloads (batch, dev/test).
  • Azure Hybrid Benefit: Use existing Windows Server and SQL Server licenses in Azure for big discount.
  • Auto-scaling: Don't pay for capacity you're not using; scale down at night, up during peak.
  • Serverless where fit: Functions and consumption tiers only bill when running.
  • Storage tiers: Hot/Cool/Cold/Archive for blob — huge savings for infrequently-accessed data.
  • Delete unused resources: Orphaned disks, old snapshots, unused public IPs quietly cost money forever.
  • Tags for chargeback: Tag resources by cost center, project, environment. Enables real cost accountability.
Tools
Pricing Calculator
Estimate costs before deploying.
TCO Calculator
Compare on-prem vs. Azure costs for migration planning.
Cost Management + Billing
Track spend, set budgets with alerts, analyze cost drivers.
Azure Advisor
Personalized recommendations including cost-saving suggestions.
◈ The war stories

Every cloud engineer has heard about the intern who spun up a huge cluster and forgot to shut it down, or the developer whose bug caused Cosmos DB to burn through six figures in a weekend. Set budgets with alerts. Set spending limits on dev subscriptions. Review the bill monthly. Runaway cost is a real risk, and it's your job to design against it.

Practice — three cloud design exercises

Sketch these on paper before reading anyone's solutions. That's where real learning happens.

◈ Exercise 1 — Modern e-commerce site on Azure

Requirements: 50,000 daily active users, ~500 concurrent, spikes 5x during holiday sales. Must be HTTPS with SSL. Product catalog ~100k items. Payment via Stripe. Order confirmation emails. 99.9% availability target.

Sketch this yourself first. Think through: what serves the web pages? Where does the product catalog live? Where does session state go? How do orders get processed reliably? Where do product images live? How do you handle the traffic spike?

Reasonable architecture: Front Door (global HTTPS + WAF + CDN for images) → App Service (scaled with auto-scale rules) → Azure SQL Database (products, orders, users) + Cache for Redis (session state, hot product data) + Blob Storage (product images). Order confirmation goes to Service Bus queue → Function → SendGrid for email. Application Insights + Log Analytics watching. Key Vault holds Stripe keys and DB connection strings. Cost Management tracks spend.

◈ Exercise 2 — Migrate a small business from on-prem to Azure

Current state: Windows Server on-prem hosting file share and a legacy .NET app with SQL Server. Two locations connected by a VPN. Windows domain with 50 users. Backups on tape.

Design a migration. Do you lift-and-shift or refactor? What's the target Azure architecture?

Reasonable phased approach: Phase 1 (lift-and-shift): Move domain controller and file share to Azure VMs; extend Entra ID Connect to sync identities. Move SQL Server to Azure SQL Managed Instance (near-full SQL compat, minimal code changes). Move legacy .NET app to App Service (may work as-is or need small changes). Connect Azure to remaining on-prem via VPN or ExpressRoute. Phase 2 (optimize): Retire domain controllers if possible, move fully to Entra ID. Break monolith into services if warranted. Use managed identities instead of AD service accounts. Phase 3: Archive tape backups; use Azure Backup with geo-redundant storage. Use Azure Migrate to plan and execute.

◈ Exercise 3 — Real-time IoT data pipeline

Requirements: 10,000 IoT sensors sending readings every 30 seconds. Need real-time dashboards, alerts on threshold breaches, and long-term storage for analytics. Compliance requires 7 years retention.

Sketch it. Think through: how do sensors send data? Where does it land? How do you process it in real-time? Where does it store long-term?

Reasonable design: Sensors → IoT Hub (device management, secure ingestion) → Event Hubs (high-throughput streaming) → Stream Analytics (real-time processing, threshold checks) → Alerts fire via Logic Apps or Functions to notification systems. Data also lands in Data Lake Storage for long-term retention (7 years, moved to Archive tier after 90 days for cost). Power BI reads from Stream Analytics for real-time dashboards; Synapse Analytics for historical queries. Cost Management with tags per project. Defender for IoT for device security.

◈ How to actually get good at this

Sketching designs is one thing. Building them is another. Spin up a free Azure account. Pick Exercise 1 and actually deploy a version of it, even at tiny scale. See how the services fit together in real life. Break things. Fix them. That's where design intuition really forms — and by the way, it's also perfect portfolio material for landing better roles.
